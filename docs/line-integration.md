## สำหรับคนที่รับงานต่อ — สัญญาทางเทคนิค

### Endpoint

```
POST /webhooks/line
```

ติดตั้งไว้**ก่อน** `express.json` โดยตั้งใจ เพราะลายเซ็นคำนวณจากไบต์ดิบที่ LINE ส่งมา
body ที่ผ่าน parser แล้ว serialise ใหม่จะต่างกันที่ช่องว่างและลำดับ key ทำให้ตรวจไม่มีวันผ่าน
และวิธีแก้ที่ล่อใจที่สุดคือปิดการตรวจทิ้ง

### การตรวจลายเซ็น (A29)

HMAC-SHA256 ของ raw body ด้วย `LINE_CHANNEL_SECRET` เทียบแบบ constant-time

| กรณี | ตอบ | บันทึกลงฐานข้อมูล |
|---|---|---|
| ลายเซ็นถูกต้อง | `200` | ✅ |
| ลายเซ็นผิด | `401` | ❌ **ไม่บันทึกอะไรเลย** |
| ไม่มีลายเซ็น | `401` | ❌ |
| ยังไม่ได้ตั้ง `LINE_CHANNEL_SECRET` | `500` | ❌ |

กรณีสุดท้ายแยกออกมาเป็น `500` โดยตั้งใจ — การขาดค่าตั้งค่าคือความผิดพลาดฝั่งการติดตั้ง
ไม่ใช่คำขอที่ไม่ถูกต้อง การรายงานเป็น `401` จะทำให้คนไล่หาปัญหาผิดทาง

คำขอที่ไม่ผ่านการตรวจ **ไม่เขียนแถวใดลงฐานข้อมูลเลย แม้แต่แถว log** เพราะผู้เรียกที่ยืนยันตัวตนไม่ได้
ต้องเขียนอะไรลงระบบไม่ได้

### การกันข้อความซ้ำ (A30)

`webhook_event_id` เป็น **primary key** ของ `line_webhook_events`

การส่งซ้ำจะแพ้การแข่ง insert แล้วถูกจับได้จาก unique constraint — **ไม่ได้อ่านก่อนเขียน**
เพราะการอ่านเช็คแล้วค่อยเขียนมีช่องว่างระหว่างสองจังหวะ ซึ่งเปิดพอดีตอน LINE ยิงซ้ำพร้อมกัน
ซึ่งเป็นสถานการณ์เดียวที่การกันซ้ำมีความหมาย

### ลำดับการทำงาน

```
รับ → ตรวจลายเซ็น → ตอบ 200 → ค่อยประมวลผล
```

ตอบก่อนทำงานเพราะ LINE ถือว่าการตอบช้าคือความล้มเหลวแล้วส่งซ้ำ
ถ้าทำงานก่อนตอบ event ที่ช้าหนึ่งตัวจะกลายเป็นพายุ retry

payload ดิบถูกบันทึกก่อนสิ่งอื่นทั้งหมด ดังนั้นถ้าการประมวลผลพัง ข้อความจะ**ช้า ไม่ใช่หาย**
แก้สาเหตุแล้ว replay แถวนั้นได้

### การจับคู่ตัวตน (A32)

| สถานะ | ผลลัพธ์ |
|---|---|
| `contacts.line_user_id` ตรง | ใช้ contact เดิม |
| ไม่ตรง | สร้าง contact ใหม่จากชื่อโปรไฟล์ LINE |
| มี lead ที่ยังเปิดอยู่ (`New` / `Qualified` / `Proposal`) | ใช้ lead เดิม บทสนทนาอยู่เส้นเดียวกัน |
| lead ปิดหมดแล้ว (`Won` / `Lost`) | สร้าง lead ใหม่ |

ข้อสุดท้ายเป็นการตัดสินใจเชิงธุรกิจ: ลูกค้าที่กลับมาทักหลังปิดดีลไปแล้ว คือ**โอกาสใหม่**
ไม่ใช่เชิงอรรถของดีลเก่า

### ข้อความขาออก (A34)

```
POST /api/leads/:id/messages
{ "text": "...", "suggestion_id": "..." }
```

`suggestion_id` ใส่เมื่อข้อความมาจากร่างของ AI — การอนุมัติส่งคือสิ่งที่ย้าย suggestion
ออกจากสถานะ `proposed`

**ฐานข้อมูลบังคับว่าข้อความขาออกต้องมีผู้อนุมัติ** ผ่าน CHECK constraint
`chk_messages_outbound_requires_approver` จึงไม่มีเส้นทางใดในโปรแกรม ทั้งที่มีอยู่และที่จะเขียนเพิ่ม
ที่ส่งข้อความหาลูกค้าโดยไม่มีคนเห็นชอบได้

แถวถูกสร้างเป็น `pending` **ก่อน**เรียก network — ถ้าโปรเซสตายกลางทาง ข้อความจะค้างและ**มองเห็น**
ไม่ใช่หายไปเงียบ ๆ ซึ่งเป็นความต่างระหว่าง "เซลส์เห็นแล้วตามต่อ" กับ "ลูกค้าถูกเมิน"

ลองส่งใหม่ได้ 3 ครั้งแบบ exponential backoff เฉพาะ `5xx`, `429` และ network error
ส่วน `4xx` ไม่ลองซ้ำ เพราะคำขอถูกปฏิเสธด้วยเหตุผลของมันเอง การยิงซ้ำแค่ถามคำถามเดิมและได้คำตอบเดิม
ขณะที่หน่วงทุกอย่างที่รออยู่ข้างหลัง

ข้อความที่ค้าง `pending` เคลียร์ด้วย

```bash
npm run messages:retry
```

## ทำไมระบบไม่ตอบอัตโนมัติ

ข้อนี้มักถูกเข้าใจว่าเป็นฟีเจอร์ที่ยังไม่เสร็จ จึงอธิบายไว้ตรงนี้

โจทย์กำหนดให้ **แยกข้อเสนอของ AI ออกจากการเขียนฐานข้อมูลและข้อความที่ส่งออกจริง**
และในเชิงออกแบบเองก็เป็นทางที่ถูก: ข้อความที่ผิดบริบทซึ่งไปถึงลูกค้าแล้ว เรียกคืนไม่ได้

ระบบจึงให้ AI ทำได้อย่างเดียวคือ**เสนอ** ส่วนการตัดสินใจส่งเป็นของคน และเส้นแบ่งนี้
ถูกบังคับที่ระดับฐานข้อมูล ไม่ใช่แค่ข้อตกลงในโค้ดที่ใครก็เผลอข้ามได้

**สิ่งที่ต้องปิดในฝั่ง LINE ด้วย:** ที่ LINE Official Account Manager → Response settings
ต้องปิด **Auto-response** และ **Greeting message** มิฉะนั้น LINE จะตอบลูกค้าเองทับข้อความ
ที่ผ่านการอนุมัติ ซึ่งทำลายหลักการทั้งหมดนี้จากนอกระบบ

## แก้ปัญหา

ดู `rest_log` ก่อนเดาเสมอ — ทุกคำขอที่เข้ามาถูกบันทึกไว้พร้อม request, response และเวลาที่ใช้

```sql
SELECT request_date, status_code, duration_ms, request_body
FROM rest_log
WHERE path LIKE '/webhooks%'
ORDER BY id DESC
LIMIT 10;
```

| อาการ | สาเหตุที่พบบ่อยที่สุด |
|---|---|
| `401` ทุกครั้ง | `LINE_CHANNEL_SECRET` ไม่ตรงกับ channel ที่ใช้ทดสอบ |
| `500` และข้อความ `Webhook not configured` | ยังไม่ได้ตั้ง `LINE_CHANNEL_SECRET` |
| LINE กด Verify ไม่ผ่าน | Webhook URL ผิด หรือยังไม่ได้เปิด **Use webhook** |
| ข้อความเข้าแต่ไม่เกิด lead | ดู `line_webhook_events.process_status` และ `error_detail` |
| ส่งออกไม่ถึง | ดู `messages.send_status` และ `error_detail` · `LINE_CHANNEL_ACCESS_TOKEN` ถูกต้องไหม |

**อย่าแก้ปัญหา `401` ด้วยการปิดการตรวจลายเซ็น** — นั่นคือการเปิดให้ใครก็ได้ยิงข้อมูลเข้าระบบ
ในนามของลูกค้าคนใดก็ได้
