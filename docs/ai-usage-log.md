# บันทึกการใช้ AI ในการพัฒนา

บันทึกนี้เก็บระหว่างทาง ไม่ได้เขียนย้อนหลัง แต่ละรายการระบุว่าสั่งอะไร ได้อะไรกลับมา
ตรวจแล้วพบอะไร และตัดสินใจอย่างไร รายการที่ **ปฏิเสธหรือแก้ผลลัพธ์ของ AI** ถูกทำเครื่องหมายไว้
เพราะเป็นสาระสำคัญของบันทึกนี้ ไม่ใช่รายการที่ AI ทำถูกตั้งแต่แรก

เครื่องมือที่ใช้: Claude Code (agent mode) สำหรับ scaffold, schema, migration, seeder และเอกสาร

## 1. Migration ที่ผ่าน syntax check แต่รันจริงไม่ได้ — REJECTED

**สั่ง:** สร้าง Sequelize migration สำหรับ 8 ตารางตาม ER diagram พร้อม CHECK constraint
ที่บังคับกฎธุรกิจ เช่น ข้อความขาออกต้องมีผู้อนุมัติ และ lead ที่ไม่มีเจ้าของต้องติดธง triage

**ได้กลับมา:** migration ครบ 8 ไฟล์ ผ่าน `node --check` ทั้งหมด และผ่านการตรวจด้วยสคริปต์
จำลองที่เขียนขึ้นเพื่อทดสอบ constraint ในระดับ JavaScript ทุกข้อ

**สิ่งที่พบตอนรันจริงกับ MySQL 8.0.46 ใน Docker:**

```
ERROR: Column 'owner_id' cannot be used in a check constraint
'chk_leads_triage_requires_no_owner': needed in a foreign key
constraint 'leads_ibfk_3' referential action.
```

MySQL ห้ามใช้ CHECK constraint กับคอลัมน์ที่มี foreign key referential action —
และไม่ใช่แค่ `ON DELETE SET NULL` เท่านั้น แต่รวมถึง `ON UPDATE CASCADE` ด้วย
ข้อจำกัดนี้ไม่มีทางเห็นจากการอ่านโค้ดหรือการตรวจ syntax เพราะเป็นกฎของ MySQL เอง

กระทบ 3 คอลัมน์ที่ถูกอ้างใน CHECK: `leads.owner_id`, `messages.approved_by`,
`ai_suggestions.decided_by`

**ตัดสินใจ:** เปลี่ยนทั้งสามคอลัมน์เป็น `onUpdate: 'NO ACTION'` และ `onDelete: 'RESTRICT'`

**ทำไมถึงเลือกทางนี้ ไม่ใช่ทิ้ง CHECK constraint:** ทางเลือกที่ง่ายกว่าคือลบ CHECK ออก
แล้วไปบังคับกฎในโค้ดแทน ซึ่งจะทำให้ migration ผ่านทันที แต่เท่ากับยกเลิกสิ่งที่ CHECK
มีค่าที่สุด คือการทำให้ **ไม่มีเส้นทางใดในโปรแกรมสร้างข้อความขาออกที่ไม่มีคนอนุมัติได้เลย**
ซึ่งเป็นเส้นแบ่งหลักของทั้งระบบ (A22)

การเปลี่ยนเป็น `RESTRICT` ไม่ได้สูญเสียอะไร เพราะ:
- id เป็น UUID ที่ไม่มีวันเปลี่ยน `ON UPDATE CASCADE` จึงไม่เคยถูกใช้อยู่แล้ว
- A14 ระบุไว้แต่แรกว่าผู้ใช้จะถูกปิดการใช้งาน ไม่ถูกลบ — `RESTRICT` คือการบังคับกฎนั้น
  ที่ระดับฐานข้อมูล ซึ่งตรงกับเจตนามากกว่า `SET NULL` เสียอีก

**บทเรียนที่นำไปใช้ต่อ:** syntax check และ unit test ที่จำลอง DB ไม่พอสำหรับงาน schema
ต้องรัน migration กับฐานข้อมูลจริงที่เป็นเวอร์ชันเดียวกับ production ก่อนถือว่าเสร็จ
และเพิ่มขั้นตอนนี้เข้า CI

**ผลการทดสอบหลังแก้** — ยิงข้อมูลที่ผิดกฎเข้าไปทั้ง 4 แบบ ฐานข้อมูลปฏิเสธครบ:

| กรณีทดสอบ | ผลลัพธ์ |
|---|---|
| ข้อความขาออกที่ไม่มีผู้อนุมัติ | `ERROR 3819` chk_messages_outbound_requires_approver |
| คำแนะนำ AI ที่ status = approved แต่ไม่มีผู้ตัดสินใจ | `ERROR 3819` chk_ai_suggestions_decision_is_attributed |
| lead ที่ไม่มีเจ้าของแต่ไม่ติดธง triage | `ERROR 3819` chk_leads_triage_requires_no_owner |
| webhook event id ซ้ำ | `ERROR 1062` duplicate entry บน PRIMARY |

## 2. Seeder ที่วนไม่รู้จบ — REJECTED

**สั่ง:** สร้าง seeder ข้อมูลสังเคราะห์ 2,000 contacts, 400 companies, 300 leads
พร้อม activity และ message ย้อนหลัง 90 วัน โดยใช้ random seed คงที่

**ได้กลับมา:** seeder ที่ดูถูกต้อง ผ่าน syntax check และตรรกะการสร้างข้อมูลอ่านแล้วสมเหตุสมผล

**สิ่งที่พบตอนลองรัน:** สคริปต์ค้างเกิน 2 นาทีโดยไม่คืนผล สาเหตุคือลูปสร้างชื่อบริษัท
ที่ไม่ซ้ำกัน 400 ชื่อ แต่คำศัพท์ที่มีให้ผสมได้เพียง `2 prefix × 16 core × 2 suffix = 64`
ชื่อที่เป็นไปได้ ลูปจึงวนหาชื่อที่ 65 ตลอดไป

**ตัดสินใจ:** เพิ่มคำขยายและหมายเลขสาขาเข้าไปในตัวสร้างชื่อเพื่อขยายพื้นที่ความเป็นไปได้
และ**เพิ่มตัวนับกันวนซ้ำที่โยน error พร้อมข้อความอธิบายเมื่อพยายามเกิน 20,000 ครั้ง**

ส่วนหลังสำคัญกว่าส่วนแรก เพราะถ้าในอนาคตมีคนแก้รายการคำศัพท์ให้สั้นลง หรือเพิ่มจำนวน
บริษัทที่ต้องการ ปัญหาเดิมจะกลับมาทันที การมีตัวนับทำให้มันล้มเหลวพร้อมบอกสาเหตุใน 1 วินาที
แทนที่จะแขวนค้างโดยไม่มีใครรู้ว่าเกิดอะไรขึ้น

**ข้อสังเกต:** บั๊กนี้จับได้เพราะเขียนสคริปต์ทดสอบที่รัน seeder จริงโดยแทนที่ชั้นฐานข้อมูล
ด้วยตัวจำลอง ถ้าอ่านโค้ดอย่างเดียวจะมองไม่เห็น เพราะโค้ดส่วนนี้ "อ่านแล้วถูก"

## 3. เลขอ้างอิงสมมติฐานในโค้ดคลาดเคลื่อน — CORRECTED

**บริบท:** ทุก comment ในโค้ดอ้างเลขสมมติฐานจาก `assumptions.md` (เช่น `// A30: ...`)
เพื่อให้ผู้อ่านโค้ดตามกลับไปหาเหตุผลได้

**สิ่งที่เกิดขึ้น:** ระหว่างทางมีการแทรกหมวดใหม่เข้าไปในเอกสาร ทำให้เลขสมมติฐานเลื่อน
แต่ comment ในโค้ดยังอ้างเลขชุดเดิม ผลคือโค้ดชี้ไปยังสมมติฐานที่ผิดเรื่องกันคนละเรื่อง
เช่น comment เรื่อง idempotency ชี้ไปที่สมมติฐานเรื่องการจับคู่ contact

**ตัดสินใจ:** ไล่ตรวจการอ้างอิงทุกจุดเทียบกับเอกสารฉบับปัจจุบันทีละรายการ แล้วแก้ให้ตรง
ไม่ใช้การแทนที่แบบเลื่อนเลขทั้งหมด เพราะการอ้างอิงบางส่วนถูกอยู่แล้วและจะพังถ้าเลื่อนตาม

**บทเรียน:** การอ้างอิงข้ามไฟล์ด้วยเลขลำดับเปราะมาก ถ้าเอกสารยาวกว่านี้ควรใช้รหัสที่ไม่
เรียงลำดับ (เช่น `AUTH-01`, `LINE-03`) ซึ่งไม่ต้องเลื่อนเมื่อมีการแทรกรายการใหม่
ในโปรเจกต์ขนาดนี้เลือกไม่รื้อ เพราะต้นทุนการแก้สูงกว่าประโยชน์ที่ได้ และบันทึกไว้เป็น
ข้อสังเกตแทน

## 4. ความแม่นยำของเวลาที่ทำให้การถามย้อนหลังตอบผิด — REJECTED

**สั่ง:** ทำตารางประวัติที่ตอบได้ว่าค่า ณ เวลาหนึ่งคืออะไร

**ได้กลับมา:** โครงสร้างที่ดูถูกต้อง ใช้ `Sequelize.DATE` สำหรับ `changed_at` และฟังก์ชัน
อ่านย้อนหลังที่กรองด้วย `changed_at > เวลาที่สนใจ` ตรรกะอ่านแล้วไม่มีอะไรผิด

**สิ่งที่พบตอนเขียนเทสต์:** เทสต์บันทึกเวลา จากนั้นเปลี่ยนชื่อบริษัท แล้วถามย้อนกลับไปที่เวลานั้น
ระบบคืน**ชื่อใหม่** แทนที่จะเป็นชื่อเก่า

สาเหตุคือ `Sequelize.DATE` แปลงเป็น `DATETIME` ของ MySQL ซึ่งเก็บ**เฉพาะวินาที** ทศนิยมถูกตัดทิ้ง
เมื่อการแก้ไขเกิดขึ้นในวินาทีเดียวกับเวลาที่ถาม เงื่อนไข `>` จึงเป็นเท็จ ระบบเลยตอบว่าไม่มีอะไรเปลี่ยน

**ตัดสินใจ:** เปลี่ยนเป็น `DATETIME(3)` ความละเอียดระดับมิลลิวินาที และเพิ่ม `id` เป็นตัวตัดสินลำดับรอง

**ทำไมถึงสำคัญกว่าที่ดู:** บั๊กนี้จะไม่ปรากฏตอนใช้งานจริงเกือบตลอดเวลา เพราะคนไม่ได้ถามย้อนหลัง
ในวินาทีเดียวกับที่แก้ข้อมูล แต่จะโผล่ตอนที่สองรายการเกิดในวินาทีเดียวกัน ซึ่งเป็นเรื่องปกติมาก
เมื่อระบบทำงานอัตโนมัติหรือมีการนำเข้าข้อมูลเป็นชุด ผลคือคำตอบผิดโดยไม่มี error ให้เห็น

## 5. Guard ที่ดูเหมือนทำงานแต่ไม่ทำอะไรเลย — REJECTED

**บริบท:** Sequelize ไม่ยิง instance hook เมื่อใช้ `Model.update()` แบบ bulk ประวัติจึงจะหายเงียบ ๆ
จึงใส่ guard ที่ `beforeBulkUpdate` ให้โยน error เมื่อมีการแก้แบบ bulk ไปโดนฟิลด์ที่ต้องบันทึก

**ได้กลับมา:** guard ที่อ่านฟิลด์ด้วย `Object.keys(options.fields)`

**สิ่งที่พบตอนเขียนเทสต์:** สั่ง bulk update ไปโดนฟิลด์ที่ track อยู่ตรง ๆ แล้ว **ไม่ throw**

สาเหตุคือใน `beforeBulkUpdate` ค่า `options.fields` เป็น **array** ของชื่อฟิลด์ ไม่ใช่ object
`Object.keys()` บน array จึงคืนดัชนี `['0','1']` ซึ่งไม่มีทางตรงกับชื่อคอลัมน์ใด ๆ

**ตัดสินใจ:** รับทั้ง array และ object แล้วรวมกับ `options.attributes` ก่อนเทียบ

**ทำไมถึงเป็นรายการที่อันตรายที่สุดในบันทึกนี้:** โค้ดที่พังแล้วส่งเสียงยังดีกว่าโค้ดที่พังแล้วเงียบ
แต่อันนี้แย่กว่าทั้งสองอย่าง คือมันสร้าง**ความรู้สึกปลอดภัยที่ไม่จริง** ทีมจะอ่านโค้ดแล้วเชื่อว่ามีการป้องกัน
ทั้งที่ไม่มี และจะไม่มีใครสงสัยจนกว่าจะพบว่าประวัติหายไปโดยไม่รู้สาเหตุ
บทเรียนคือ guard ทุกตัวต้องมีเทสต์ที่พิสูจน์ว่ามัน **ปฏิเสธ** ของผิดจริง ไม่ใช่แค่ยอมรับของถูก

## 6. เวลาที่ถูกตัดทศนิยมโดยไม่มีใครบอก — CORRECTED

**บริบท:** ตาราง `rest_log` มีทั้ง `request_date`, `response_date` และ `created_at`
โดย `created_at` คือเวลาที่แถวถูกเขียนจริง ซึ่งเกิดหลังส่ง response แล้ว
ส่วนต่างระหว่างสองค่าหลังคือความหน่วงของตัวระบบบันทึกเอง

**สิ่งที่พบ:** คิวรีตรวจสอบคืนค่าความหน่วงเป็น **ลบ 656 มิลลิวินาที** — แปลว่าแถวถูกเขียน
ก่อนที่ response จะถูกส่ง ซึ่งเป็นไปไม่ได้

**สาเหตุ:** คอลัมน์ใน MySQL เป็น `datetime(3)` ถูกต้องแล้ว แต่ Sequelize เป็นผู้จัดการ
`createdAt` ให้อัตโนมัติเมื่อตั้ง `timestamps: true` และใช้ชนิด `DataTypes.DATE` ที่**ไม่มี
ความละเอียด** เวลาจึงถูกจัดรูปแบบโดยตัดเศษวินาทีทิ้งก่อนส่งเข้าฐานข้อมูล ค่าที่เก็บจึงลงท้าย
ด้วย `.000` เสมอ และดูเหมือนย้อนเวลากลับไปก่อน response ที่มันบันทึก

**ตัดสินใจ:** ประกาศ `createdAt` ในโมเดลด้วย `DataTypes.DATE(3)` อย่างชัดเจน แทนที่จะ
ปล่อยให้ Sequelize เลือกให้ หลังแก้ค่าความหน่วงกลายเป็น **บวก 1 มิลลิวินาที** ตามที่ควรเป็น

**เจอซ้ำอีกจุดหนึ่ง:** หลังแก้ `rest_log` แล้ว ปัญหาเดียวกันโผล่ที่ timeline ของ lead
โดยรายการ `message_received` แสดงอยู่**เหนือ** `lead_created` ทั้งที่ lead ต้องมีอยู่ก่อนข้อความ
สาเหตุเดียวกันเป๊ะ — ทั้งสองแถวถูกเขียนในทรานแซกชันเดียวกันจึงอยู่ในวินาทีเดียวกัน
และคอลัมน์ที่เก็บแค่ระดับวินาทีเรียงลำดับให้ไม่ได้ MySQL จึงคืนมาตามใจ
ซึ่งสำหรับเซลส์ที่กำลังอ่านบทสนทนาอยู่ก็คือข้อมูลที่ผิด

แก้โดยขยายความละเอียดของคอลัมน์ที่ใช้เรียง timeline และบทสนทนาทั้งหมดเป็น `DATETIME(3)`
พร้อมประกาศชนิดในโมเดลด้วย ผลคือ `lead_created` ที่ `.291` มาก่อน `message_received` ที่ `.300`
ตามความเป็นจริง

**บทเรียนที่ชัดขึ้นจากการเจอซ้ำ:** ปัญหานี้ไม่ได้อยู่ที่โค้ดจุดใดจุดหนึ่ง แต่เป็น**ค่าเริ่มต้นของเครื่องมือ
ที่ขัดกับเจตนาของ schema** จึงจะโผล่ทุกที่ที่มีการเรียงลำดับด้วยเวลา การแก้เฉพาะจุดที่เจอครั้งแรก
จึงไม่พอ ต้องไล่ดูทุกคอลัมน์ที่ถูกใช้ใน `ORDER BY`

**ทำไมถึงน่าสนใจ:** ทั้งฝั่ง migration และฝั่งฐานข้อมูลถูกต้องทุกอย่าง ตรวจ schema แล้วเห็น
`datetime(3)` ชัดเจน ปัญหาอยู่ที่ชั้น ORM ซึ่งไม่มีใครมองเพราะไม่ได้เขียนเอง
บทเรียนคือ **การประกาศชนิดไว้ใน migration ไม่ได้รับประกันว่าค่าที่เขียนจะมีความละเอียดเท่ากัน**
ต้องยืนยันด้วยการอ่านข้อมูลจริงกลับมาดู และเป็นบั๊กที่จะไม่มีวันปรากฏถ้าไม่ได้เขียนคิวรีเปรียบเทียบ
สองคอลัมน์เวลาเข้าหากัน
