# สมมติฐานและขอบเขตงาน

โจทย์เว้นรายละเอียดหลายจุดไว้โดยตั้งใจ ผมเลือกไม่หยุดรอคำตอบ แต่ตัดสินใจแล้วบันทึกเหตุผลไว้ทุกข้อ
แต่ละข้อเขียนในรูปแบบเดียวกัน: **โจทย์เว้นอะไรไว้ → ตัดสินใจอย่างไร → เพราะอะไร**
ส่วนที่เลือก *ไม่ทำ* อยู่ท้ายเอกสาร พร้อมประมาณการเวลาถ้าต้องทำเพิ่มภายหลัง

บริบทที่กำหนดการตัดสินใจเกือบทุกข้อ: **16 ชั่วโมงโฟกัส** วิศวกรคนเดียว เครื่องมือใช้ภายในสำหรับ
ทีมขาย 20 คน (~2,000 contacts, ~300 active leads) ระบบขนาดเล็กและขอบเขตชัด
การตัดสินใจทั้งหมดจึงเลือก "ทำให้ครบเส้นและใช้งานได้จริง" มากกว่า "ทำให้ครบทุกฟีเจอร์"

---

| A2 | บัญชีสาธิต 2 บัญชี: `sales@demo.local` (role `sales`) และ `manager@demo.local` (role `manager`) ระบุรหัสผ่านไว้ใน README | ผู้ประเมินต้องเข้าระบบได้ภายในไม่กี่วินาที และบัญชีเหล่านี้ใช้ได้กับข้อมูลสังเคราะห์เท่านั้น |

| A4 | ไม่ทำ SSO, reset password, ยืนยันอีเมล และ MFA | เครื่องมือใช้ภายใน ผู้เช่ารายเดียว ระบุไว้ใน production next steps แล้ว |

| A8 | ข้อมูลตั้งต้น: 2,000 contacts, ~400 companies, 300 active leads กระจายครบทั้ง 5 stage พร้อม activities และ messages ที่กระจายเวลาย้อนหลัง 90 วัน ทั้งหมดเป็นข้อมูลสังเคราะห์ที่สร้างด้วย random seed คงที่ | โจทย์บังคับใช้ข้อมูลสังเคราะห์ การตรึง seed ทำให้สาธิตซ้ำได้เหมือนเดิมและภาพหน้าจอไม่เปลี่ยนไปมา |
| A9 | เก็บจำนวนเงินเป็นจำนวนเต็มหน่วยบาท (`value_thb`) ไม่ใช้ decimal หรือชนิดสกุลเงิน | สกุลเดียว มูลค่าดีลเป็นบาทเต็มจำนวน เลี่ยงปัญหาปัดเศษโดยไม่ต้องลากไลบรารีจัดการเงินเข้ามา |
| A10 | เก็บเวลาเป็น UTC แสดงผลเป็น `Asia/Bangkok` | แนวปฏิบัติมาตรฐาน และทีมอยู่ภูมิภาคเดียว |

## 3. มาตรฐานคอลัมน์ การปิดใช้งาน และการตรวจสอบย้อนหลัง

ระบบองค์กรจำนวนมากกำหนดให้ทุกตารางมีคอลัมน์ชุดเดียวกัน (`create_by`, `update_by`, `status_id`,
`active`, `ip`) ผมพิจารณาแนวทางนี้แล้วเลือกใช้เพียงบางส่วน โดยแยกตามว่าคอลัมน์นั้นมีความหมายกับ
ตารางนั้นจริงหรือไม่

| # | สมมติฐาน | เหตุผล |
|---|---|---|
| A11 | `created_at` และ `updated_at` มีครบ**ทุกตาราง** | Sequelize จัดการให้อัตโนมัติ ไม่มีต้นทุนและได้ข้อมูลว่าแถวถูกแตะครั้งล่าสุดเมื่อไรฟรี ๆ |
| A12 | `created_by` และ `updated_by` มี**เฉพาะตารางที่มนุษย์เป็นผู้สร้างหรือแก้ไข** คือ `companies`, `contacts`, `leads` ส่วน `activities` ใช้ `actor_id` แทนเพราะสื่อความหมายตรงกว่า | `messages` ขาเข้ามาจากลูกค้า `line_webhook_events` มาจากระบบ และ `ai_suggestions` มาจากโมเดล การใส่คอลัมน์ผู้สร้างในตารางเหล่านี้จะเป็น null ตลอดเวลาและทำให้เข้าใจผิดว่ามีคนทำ |
| A13 | **ไม่ใช้ `status_id` แบบรวมศูนย์** แต่ละตารางใช้ ENUM ของตัวเอง: `leads.stage`, `messages.send_status`, `ai_suggestions.status`, `line_webhook_events.process_status` | สถานะของแต่ละ entity มีความหมายคนละชุดโดยสิ้นเชิง ENUM เฉพาะตารางทำให้ฐานข้อมูลปฏิเสธค่าที่ผิดได้จริง ซึ่งตรงกับที่โจทย์กำหนดเรื่อง meaningful constraints ส่วน `status_id` ที่ชี้ไปตาราง lookup กลางแทบไม่กันอะไรเลย และทำให้อ่านคิวรีไม่ออกโดยไม่เปิดตารางอ้างอิงควบคู่ |
| A14 | `is_active` มี**เฉพาะ 3 ตาราง**: `users`, `contacts`, `companies` และ**ไม่มีการลบถาวร**ในสามตารางนี้ | พนักงานลาออกแล้วลบทิ้งไม่ได้ เพราะ `leads.owner_id` และ `activities.actor_id` อ้างถึงอยู่ ประวัติทั้งหมดจะพังตาม การปิดใช้งานจึงเป็นทางเดียวที่รักษา audit trail ไว้ได้ ส่วน `leads` ไม่ต้องมีเพราะ stage `Lost` ทำหน้าที่นี้แล้ว และตารางบันทึกประวัติไม่มีวันถูกปิดใช้งาน |
| A15 | **ไม่เก็บ `ip` ในตารางธุรกิจ** เก็บเฉพาะเหตุการณ์การยืนยันตัวตน (เข้าสู่ระบบสำเร็จและล้มเหลว) ไว้ใน log ที่มีอายุ 90 วัน | IP address เป็นข้อมูลส่วนบุคคลตาม PDPA การเก็บลงทุกแถวโดยไม่มีวัตถุประสงค์เฉพาะเพิ่มภาระเมื่อเจ้าของข้อมูลใช้สิทธิขอลบ และขยายความเสียหายหากฐานข้อมูลรั่ว ส่วนการเก็บเฉพาะเหตุการณ์ยืนยันตัวตนมีวัตถุประสงค์ชอบธรรมชัดเจนคือการตรวจจับการเข้าถึงผิดปกติ |
| A16 | **ไม่มีตาราง audit แบบ field-level** การตรวจสอบย้อนหลังระดับธุรกิจใช้ `activities` ซึ่งบันทึกการเปลี่ยน stage การเปลี่ยนเจ้าของ การส่งข้อความ และการอนุมัติผลจาก AI พร้อมผู้กระทำและเวลา | นี่คือระดับที่โจทย์ต้องการเมื่อระบุว่าห้ามสูญเสีย audit trail ส่วนตารางบันทึกการเปลี่ยนแปลงรายฟิลด์ทำให้ทุกการเขียนช้าลงและซับซ้อนขึ้น อีกทั้งต้องมีหน้าจอมาอ่านจึงจะมีประโยชน์ หากมีข้อกำหนด compliance ที่เข้มขึ้นในอนาคต แนวทางคือเพิ่มตาราง audit ที่เขียนผ่าน hook ระดับแอปพลิเคชัน ไม่ใช่กระจายคอลัมน์ตรวจสอบไปทุกตาราง |
| A17 | **เก็บสำเนาข้อมูล ณ เวลานั้น (point-in-time snapshot) เพียง 2 จุด**: `activities.from_stage` / `to_stage` เก็บเป็นค่า stage ตรง ๆ ไม่ใช่ FK และ `ai_suggestions.context_snapshot` เก็บข้อมูล lead ที่โมเดลเห็นตอนสร้างคำแนะนำ พร้อม `model` และ `prompt_version` ที่เหลือทั้งหมดใช้การ join กับค่าปัจจุบัน | การแช่ค่าไว้เหมาะกับกรณีที่ค่าในอดีตมีผลผูกพันและต้องตอบให้ได้ว่า ตอนนั้นเป็นอย่างไร สองจุดนี้เข้าเงื่อนไข: ประวัติการย้าย stage ต้องอ่านออกแม้ pipeline ถูกเปลี่ยนชื่อ และคำถามว่าทำไม AI ให้คะแนนเท่านี้ต้องตอบได้แม้ lead ถูกแก้ไปแล้ว ส่วนชื่อ contact หรือชื่อบริษัทไม่เข้าเงื่อนไข เพราะเซลส์ต้องเห็นค่าล่าสุดเสมอ การแช่ชื่อเก่าไว้จะกลายเป็นข้อผิดพลาด ไม่ใช่คุณสมบัติ |

## 4. พฤติกรรมของ pipeline

| # | สมมติฐาน | เหตุผล |
|---|---|---|
| A18 | ใช้ 5 stage ตามโจทย์แบบตายตัวเป็น enum: `New`, `Qualified`, `Proposal`, `Won`, `Lost` | โจทย์ระบุชื่อมาให้ชัดเจน ระบบตั้งค่า pipeline เองเป็นฟีเจอร์ระดับผลิตภัณฑ์ ไม่ใช่ข้อกำหนดของ MVP |
| A19 | เปลี่ยน stage ได้ทุกทิศทางรวมถึงถอยหลัง ทุกการเปลี่ยนเขียน `Activity` บันทึกว่าใครย้าย จากอะไรไปอะไร เมื่อไร | งานขายจริงมีดีลถอยหลังเสมอ และ audit trail ที่โจทย์บังคับสำคัญกว่าการบังคับ state machine |
| A20 | `Won` และ `Lost` ถือเป็นปลายทางในเชิงรายงาน แต่ไม่ล็อก เปิดดีลกลับมาได้และถูกบันทึก | เหตุผลเดียวกับ A19 |
| A21 | เปลี่ยน stage ผ่านปุ่มหรือ dropdown ไม่ทำ drag-and-drop | drag-and-drop ใช้เวลา 2-3 ชั่วโมงรวมการรองรับ touch แต่ไม่เพิ่มความสามารถที่ถูกประเมิน ระบุไว้ใน next steps |

## 5. AI copilot

| # | สมมติฐาน | เหตุผล |
|---|---|---|
| A22 | **AI ไม่เขียนลงตารางธุรกิจ และไม่ส่งอะไรออกไปข้างนอกเด็ดขาด** ทุกผลลัพธ์ถูกบันทึกลง `ai_suggestions` ด้วย `status = 'proposed'` ต้องมีคนกดจึงเปลี่ยนเป็น `approved` หรือ `rejected` และหลังจากนั้นระบบจึงแก้ lead หรือส่งข้อความ | นี่คือเส้นแบ่งที่สำคัญที่สุดของงานนี้ โจทย์บังคับให้แยก AI suggestion ออกจาก confirmed write และข้อความขาออก และในเชิงออกแบบเองก็เป็นทางที่ถูกต้อง |
| A23 | copilot คืนผลลัพธ์ 4 อย่างในการเรียกครั้งเดียว เป็น JSON ที่มีโครงสร้าง: `summary`, `score` (0-100) พร้อมเหตุผล, `next_best_action`, `draft_line_reply` | โจทย์ระบุมาครบ 4 อย่างนี้ การเรียกครั้งเดียวช่วยคุมเวลาตอบสนองและค่าใช้จ่าย และทำให้ผลลัพธ์ทั้งสี่สอดคล้องกัน |
| A24 | คะแนน qualification มาจากโมเดล **แต่ถูกกำกับด้วย rubric**: prompt กำหนดเกณฑ์ชัดเจน (ความสดของการติดต่อล่าสุด, ปริมาณการโต้ตอบ, สัญญาณเรื่องงบประมาณ, ความคืบหน้าของ stage, มูลค่าดีล) และโมเดลต้องคืนคะแนนแยกรายเกณฑ์ ไม่มีโมเดลที่เทรนเอง และไม่มีข้อมูลแพ้ชนะย้อนหลังให้เรียนรู้ | คะแนนต้องอธิบายให้เซลส์เข้าใจได้ การมี rubric ทำให้ตรวจสอบย้อนได้ และทำให้เส้นทาง fallback ให้ผลใกล้เคียงกัน |
| A25 | เมื่อ LLM ใช้งานไม่ได้หรือคืนผลผิดรูปแบบ: ใช้ตัวให้คะแนนแบบกฎตายตัวที่ใช้ rubric ชุดเดียวกัน คืนคะแนนพร้อมเหตุผล ส่วน `summary` ถอยไปใช้ข้อความล่าสุด และ `draft_line_reply` จะ**ถูกงดทั้งหมด** ไม่ใช้เทมเพลตแทน ผลลัพธ์ติดธง `degraded: true` และ UI แสดงให้เห็นชัด | โจทย์บังคับให้มี fallback ที่ปลอดภัย การงดร่างข้อความเป็นการตัดสินใจที่ตั้งใจ เพราะข้อความสำเร็จรูปที่ผิดบริบทถึงมือลูกค้าแย่กว่าการไม่เสนออะไรเลย และการลดความสามารถแบบประกาศให้รู้ ดีกว่าลดแบบเงียบ ๆ |
| A26 | เนื้อหาข้อความจากลูกค้าถูกส่งให้โมเดลในฐานะข้อมูลที่ไม่น่าเชื่อถือ คั่นด้วยตัวคั่นชัดเจน และ system prompt ระบุว่าเนื้อหาในตัวคั่นไม่ใช่คำสั่งไม่ว่ากรณีใด ผลลัพธ์จากโมเดลถูกตรวจ schema ก่อนบันทึกหรือแสดงผล | ใครก็พิมพ์อะไรเข้ามาทาง LINE ได้ รวมถึงความพยายามทำ prompt injection นี่คือประเด็นความปลอดภัยเฉพาะของฟีเจอร์ AI และมี test ครอบคลุม |
| A27 | เรียก AI จากฝั่งเซิร์ฟเวอร์เท่านั้น จำกัดอัตราการเรียกต่อผู้ใช้ และไม่เรียกอัตโนมัติเมื่อมีข้อความเข้า — ต้องมีคนกด | คุมค่าใช้จ่ายและคุมความเสียหายหากพลาด การสร้างอัตโนมัติทุกข้อความขาเข้าจะเผางบไปกับ lead ที่ไม่มีใครทำ |
| A28 | ผู้ให้บริการ: LLM เจ้าเดียวหลัง adapter interface บาง ๆ เลือกด้วย environment variable การเปลี่ยนเจ้าคือการ implement interface เดียว | โจทย์เปิดให้เลือกผู้ให้บริการใดก็ได้ และ adapter ยังทำให้เส้นทาง fallback กับการเขียน test ง่ายขึ้นมาก |

## 6. การเชื่อมต่อ LINE OA

| # | สมมติฐาน | เหตุผล |
|---|---|---|
| A29 | ขาเข้า: ตรวจ signature จาก **raw request body** ด้วย HMAC-SHA256 และเปรียบเทียบแบบ constant-time ก่อนแตะ payload ถ้าไม่ผ่านตอบ 401 และไม่บันทึกอะไรเลย | โจทย์บังคับ และเป็นจุดที่พลาดแบบเงียบ ๆ ได้ง่ายที่สุด เพราะถ้า body parser ทำงานก่อน การตรวจจะพังโดยไม่มีสัญญาณ แล้ววิธีแก้ที่ล่อใจคือปิดการตรวจทิ้ง |
| A30 | ใช้ `webhookEventId` เป็นกุญแจกันซ้ำ เก็บเป็น primary key ของ `line_webhook_events` ตรวจจับข้อความซ้ำจาก unique constraint ตอน insert ไม่ใช่การอ่านก่อนเขียน | LINE จะยิงซ้ำเมื่อ timeout การอ่านก่อนเขียนมีช่วงว่างให้เกิด race condition แต่ constraint ไม่มี |
| A31 | endpoint บันทึก raw event แล้วตอบ `200` ทันที ส่วนการจับคู่ สร้าง lead และงานต่อเนื่องทำหลังตอบกลับ | LINE ต้องการการตอบรับที่เร็ว และการเก็บ payload ดิบไว้ก่อนแปลว่าถ้า logic พัง ยัง replay ได้แทนที่จะทำข้อความหาย |
| A32 | การจับคู่ตัวตน: `contacts.line_user_id` เป็น unique ถ้าไม่รู้จักผู้ส่ง ระบบสร้าง `Contact` และ `Lead` ใหม่ที่ stage `New` โดยยังไม่มีเจ้าของ และติดธงรอคัดกรอง | นี่คือหัวใจของการเชื่อมต่อ — lead ขาเข้าต้องลงระบบเองโดยเซลส์ไม่ต้องมานั่งพิมพ์ซ้ำ |
| A33 | เก็บชื่อที่แสดงบนโปรไฟล์ LINE ตอนติดต่อครั้งแรก แต่**ไม่**ถือเป็นชื่อหลักของ contact เมื่อมีคนแก้ไขแล้ว | ชื่อที่แสดงเปลี่ยนได้ตลอดและมักไม่ใช่ชื่อจริงของบุคคลนั้น |
| A34 | ขาออกต้อง**ผ่านการอนุมัติ**: ร่างข้อความถูกเก็บเป็น `ai_suggestion` เมื่อมีคนอนุมัติจึงสร้าง `Message` ด้วย `send_status = 'pending'` แล้วส่งไป LINE ส่งสำเร็จเปลี่ยนเป็น `sent` ส่งไม่สำเร็จเปลี่ยนเป็น `failed` พร้อมเก็บ error ไว้ | ต่อเนื่องจาก A22 โดยตรง และยังได้จุดสำหรับลองส่งใหม่ในตัว |
| A35 | ลองส่งใหม่ได้ไม่เกิน 3 ครั้ง แบบ exponential backoff เฉพาะกรณี 5xx และ network error ส่วน 4xx ไม่ลองซ้ำ ข้อความที่ค้างสถานะ `pending` ยังแสดงใน UI ไม่หายไปเฉย ๆ | LINE ล่มควรทำให้ข้อความช้า ไม่ใช่ทำให้ข้อความหาย ส่วนการลองซ้ำกับ 4xx คือการยิงคำขอที่ถูกปฏิเสธไปแล้วซ้ำอีก |
| A36 | `MockLineAdapter` ใช้ interface เดียวกับตัวจริง เลือกด้วย environment variable ทั้งการพัฒนาบนเครื่องและ test suite ทั้งหมดรันผ่านตัวนี้ | โจทย์บังคับให้มี และทำให้ test เร็วและไม่ต้องพึ่งเครือข่าย |
| A37 | เนื้อหาแบบอื่น (สติกเกอร์ รูป ไฟล์ ตำแหน่ง) บันทึกชนิดไว้แต่แสดงเป็น placeholder ใน timeline และส่งเฉพาะข้อความตัวอักษรให้ AI | การจัดการสื่อเป็นปัญหาเรื่องพื้นที่เก็บและการกลั่นกรอง ซึ่งเกินขอบเขต 16 ชั่วโมงไปมาก |

## 7. การติดตั้ง การตั้งค่า และการดูแลระบบ

| # | สมมติฐาน | เหตุผล |
|---|---|---|
| A38 | ติดตั้งบนแพลตฟอร์มจัดการเดียว: Node/Express API + Next.js UI + MySQL แบบ managed สถานะทั้งหมดอยู่ใน MySQL ไม่มี cache ในหน่วยความจำที่การสาธิตต้องพึ่งพา | โจทย์บังคับว่า core flow ต้องรอด refresh และ restart |
| A39 | รัน migration เป็นขั้นตอนหนึ่งของการ deploy ไม่รันอัตโนมัติตอนแอปเริ่มทำงาน | การ auto-migrate ตอน boot คือวิธีที่ migration พังตัวเดียวทำให้ทุก instance ล้มพร้อมกัน |
| A40 | secret อยู่ใน environment variable ของแพลตฟอร์มเท่านั้น `.env.example` ระบุตัวแปรครบทุกตัวด้วยค่า placeholder และเป็นไฟล์ env เพียงไฟล์เดียวที่ commit ไม่มี secret ปรากฏใน repository ใน log หรือในวิดีโอสาธิต | โจทย์บังคับ และการจัดการ secret ยังเป็นหนึ่งใน red flag ที่ JD ระบุไว้ชัด |
| A41 | log เป็น JSON มีโครงสร้าง พร้อม request ID ที่ส่งต่อตลอดวงจรคำขอ ปกปิด LINE user ID และเนื้อความ เหลือเพียงตัวระบุและความยาว | ดีบักได้โดยไม่เปลี่ยนที่เก็บ log ให้กลายเป็นสำเนาบทสนทนาลูกค้าที่ไม่มีใครดูแล |
| A42 | การเฝ้าระวังเป็น**เอกสาร ไม่ได้ติดตั้งจริง**: README ระบุสัญญาณที่ควรตั้งการแจ้งเตือน (อัตรา 401 ของ webhook, ความหน่วงในการประมวลผล webhook, อัตราความผิดพลาดและ fallback ของ LLM, อัตราส่งข้อความล้มเหลว, ข้อความที่ค้างสถานะ `pending`) พร้อมบอกว่าจะส่งไปที่ไหน | การต่อระบบเฝ้าระวังจริงไม่คุ้มกับชั่วโมงที่เหลือ แต่การระบุสัญญาณที่ถูกต้องแสดงวิจารณญาณชุดเดียวกัน |
| A43 | **ภาษา: TypeScript ฝั่ง Next.js UI และ JavaScript + zod ฝั่ง Express API** โดย schema ของ zod เป็นตัวตรวจทั้ง request ที่เข้า API ทุกเส้น payload ที่ LINE ยิงเข้ามา และ JSON ที่โมเดลคืนกลับ | ข้อมูลที่มีความเสี่ยงทั้งหมดในระบบนี้มาจากภายนอก คือ webhook payload และผลลัพธ์จาก LLM ซึ่ง static type มองไม่เห็นเลยเพราะตรวจเฉพาะตอน compile การลงทุนกับ schema validation ที่ทำงานตอน runtime จึงคุ้มกว่าภายใต้เวลา 16 ชั่วโมง ส่วนฝั่ง UI ใช้ TypeScript เพราะเป็นค่าเริ่มต้นของ Next.js อยู่แล้วจึงไม่มีต้นทุนเพิ่ม เหตุผลที่ไม่ใช้ TypeScript ทั้งระบบคือ Sequelize v6 ต้องประกาศ type แยกจาก init และ sequelize-cli ยังรัน migration จาก JavaScript อยู่ดี รวมแล้วเพิ่มราว 2 ชั่วโมง โดยไม่เพิ่มความปลอดภัยตรงจุดที่ระบบนี้เสี่ยงจริง |

## 8. สิ่งที่เลือกไม่ทำ

ทุกข้อคือการตัดออกอย่างตั้งใจ ไม่ใช่การมองข้าม เวลาที่ประเมินเป็นการประมาณของผมเอง

| สิ่งที่ตัด | เหตุผล | เวลาถ้าจะทำเพิ่ม |
|---|---|---|
| pipeline แบบลากวาง | เปลี่ยน stage ด้วยปุ่มให้ผลเท่ากันในเชิงหน้าที่ | ~3 ชม. |
| แดชบอร์ดรายงานและการพยากรณ์ | ไม่มี flow ที่ถูกประเมินข้อใดต้องใช้ | ~1 วัน |
| อีเมลและช่องทางอื่น | โจทย์กำหนดขอบเขตไว้ที่ LINE OA | ~2 วันต่อช่องทาง |
| นำเข้า/ส่งออกข้อมูลจำนวนมาก | ข้อมูลตั้งต้นครอบคลุมความต้องการของการสาธิตแล้ว | ~4 ชม. |
| custom field และ pipeline ที่ตั้งค่าได้ | เป็นฟีเจอร์ระดับผลิตภัณฑ์ ไม่ใช่ MVP | ~1 สัปดาห์ |
| อัปเดตแบบเรียลไทม์หลายผู้ใช้ | ผู้ใช้ 20 คนบน 300 lead แทบไม่ชนกัน การ poll ในหน้า lead เพียงพอ | ~2 วัน |
| หน้าดู audit log แยกต่างหาก | activity ถูกบันทึกและแสดงใน timeline ของ lead อยู่แล้ว แค่ไม่มีหน้าผู้ดูแลแยก | ~1 วัน |
| หน้าจอกู้คืนเรคคอร์ดที่ปิดใช้งาน | `is_active` ทำหน้าที่แทนการลบแล้ว (A14) แต่ยังไม่มีหน้าจอสำหรับดูและเปิดใช้งานกลับ ต้องแก้ผ่านฐานข้อมูล | ~4 ชม. |
| การรองรับหลายภาษา | เนื้อหาไทยและอังกฤษแสดงผลถูกต้อง แต่ส่วนติดต่อผู้ใช้เป็นอังกฤษอย่างเดียว | ~1 วัน |
| การตรวจสอบการเข้าถึงอย่างเป็นทางการ | ใช้ semantic HTML และควบคุมด้วยคีย์บอร์ดได้ แต่ยังไม่ได้ตรวจตามมาตรฐาน WCAG | ~1 วัน |

## 9. ความเสี่ยงที่รับไว้อย่างรู้ตัว

- **คุณภาพผลลัพธ์ของ LLM ยังไม่ถูกตรวจสอบกับผลการขายจริง** คะแนนอธิบายได้ แต่ยังไม่พิสูจน์ว่าทำนายได้ วิธีลดความเสี่ยงคือนำเสนอเป็นสัญญาณสำหรับจัดลำดับ ไม่ใช่เป็นคำตัดสิน
- **ติดตั้งภูมิภาคเดียวและไม่มี dead-letter queue** ข้อความที่ LINE ส่งมาระหว่าง deploy อาจตกหล่น การ retry ของ LINE ครอบคลุมกรณีส่วนใหญ่ และตาราง raw event ทำให้ replay ได้ แต่ยังไม่มีคิวรองรับจริง
- **ยังไม่ได้ทดสอบภาระงาน** ขนาดระบบมาจากการให้เหตุผลตามตัวเลขในโจทย์ ไม่ได้มาจากการวัด
- **รหัสผ่านบัญชีสาธิตเปิดเผยโดยตั้งใจ** ระบบที่ติดตั้งมีเฉพาะข้อมูลสังเคราะห์ และควรปิดหลังการประเมินเสร็จสิ้น
