# สมมติฐานและขอบเขตงาน

โจทย์เว้นรายละเอียดหลายจุดไว้โดยตั้งใจ ผมเลือกไม่หยุดรอคำตอบ แต่ตัดสินใจแล้วบันทึกเหตุผลไว้ทุกข้อ
แต่ละข้อเขียนในรูปแบบเดียวกัน: **โจทย์เว้นอะไรไว้ → ตัดสินใจอย่างไร → เพราะอะไร**
ส่วนที่เลือก *ไม่ทำ* อยู่ท้ายเอกสาร พร้อมประมาณการเวลาถ้าต้องทำเพิ่มภายหลัง

บริบทที่กำหนดการตัดสินใจเกือบทุกข้อ: **16 ชั่วโมงโฟกัส** วิศวกรคนเดียว เครื่องมือใช้ภายในสำหรับ
ทีมขาย 20 คน (~2,000 contacts, ~300 active leads) ระบบขนาดเล็กและขอบเขตชัด
การตัดสินใจทั้งหมดจึงเลือก "ทำให้ครบเส้นและใช้งานได้จริง" มากกว่า "ทำให้ครบทุกฟีเจอร์"

## 3. มาตรฐานคอลัมน์ การปิดใช้งาน และการตรวจสอบย้อนหลัง

ระบบองค์กรจำนวนมากกำหนดให้ทุกตารางมีคอลัมน์ชุดเดียวกัน (`create_by`, `update_by`, `status_id`,
`active`, `ip`) ผมพิจารณาแนวทางนี้ทีละคอลัมน์ว่ามีความหมายกับตารางนั้นจริงหรือไม่ ผลคือ
**รับมาเกือบทั้งหมด**: `created_by` / `updated_by` มีครบทุกตารางธุรกิจโดยระบบเติมเองผ่าน hook (A12)
และ `is_active` มีในตารางที่การปิดใช้งานมีความหมาย (A14) ส่วนที่ไม่รับมี 2 อย่างคือ `status_id`
แบบรวมศูนย์ (A13) และ `ip` ในตารางธุรกิจ (A15) พร้อมเหตุผลกำกับทั้งคู่

นอกจากนี้ยังเพิ่มสิ่งที่ชุดมาตรฐานไม่มีแต่ระบบนี้ต้องการ คือตารางประวัติ `tbl_audit_history` (A16)
และคอลัมน์ snapshot ของเรคคอร์ดที่เกี่ยวข้อง (A17)

| # | สมมติฐาน | เหตุผล |
|---|---|---|
| A11 | `created_at` และ `updated_at` มีครบ**ทุกตาราง** | Sequelize จัดการให้อัตโนมัติ ไม่มีต้นทุนและได้ข้อมูลว่าแถวถูกแตะครั้งล่าสุดเมื่อไรฟรี ๆ |
| A12 | **`created_by` และ `updated_by` มีครบทุกตารางธุรกิจทั้ง 8 ตาราง** เติมอัตโนมัติจาก `actorId` ที่ส่งมากับคำสั่งผ่าน hook ใน `lib/authorship.js` ไม่ต้องเขียนเองทีละจุด · `null` แปลว่า**ระบบเป็นผู้ทำ** ไม่ใช่ข้อมูลขาด · `updated_by` เปลี่ยนเฉพาะเมื่อมีข้อมูลอื่นเปลี่ยนจริง · `tbl_audit_history` ไม่มีคู่นี้เพราะมี `changed_by` ซึ่งคือผู้สร้างแถวนั้นอยู่แล้ว | คอลัมน์ที่ต้องอาศัยให้นักพัฒนาทุกคนจำว่าต้องใส่ คือคอลัมน์ที่จะผิดในเส้นทางที่ไม่มีใครนึกถึง ซึ่งมักเป็นเส้นทางที่คำถามจากฝ่ายสนับสนุนไปตกพอดี การให้ hook เป็นผู้เติมจึงเป็นเงื่อนไขที่ทำให้คอลัมน์นี้เชื่อถือได้ ส่วนการปล่อยให้เป็น `null` เมื่อระบบทำ ดีกว่าการสร้างบัญชีตัวแทนขึ้นมาใส่ เพราะบัญชีปลอมคือคำตอบที่ผิดซึ่งต้องมาตามแก้ความเข้าใจทีหลัง และการเพิ่มคอลัมน์ผู้สร้างลงในตาราง audit จะเป็นข้อเท็จจริงเดียวกันที่มีสองชื่อ |
| A13 | **ไม่ใช้ `status_id` แบบรวมศูนย์** แต่ละตารางใช้ ENUM ของตัวเอง: `leads.stage`, `messages.send_status`, `ai_suggestions.status`, `line_webhook_events.process_status` | สถานะของแต่ละ entity มีความหมายคนละชุดโดยสิ้นเชิง ENUM เฉพาะตารางทำให้ฐานข้อมูลปฏิเสธค่าที่ผิดได้จริง ซึ่งตรงกับที่โจทย์กำหนดเรื่อง meaningful constraints ส่วน `status_id` ที่ชี้ไปตาราง lookup กลางแทบไม่กันอะไรเลย และทำให้อ่านคิวรีไม่ออกโดยไม่เปิดตารางอ้างอิงควบคู่ |
| A14 | `is_active` มี**เฉพาะ 3 ตาราง**: `users`, `contacts`, `companies` และ**ไม่มีการลบถาวร**ในสามตารางนี้ | พนักงานลาออกแล้วลบทิ้งไม่ได้ เพราะ `leads.owner_id` และ `activities.actor_id` อ้างถึงอยู่ ประวัติทั้งหมดจะพังตาม การปิดใช้งานจึงเป็นทางเดียวที่รักษา audit trail ไว้ได้ ส่วน `leads` ไม่ต้องมีเพราะ stage `Lost` ทำหน้าที่นี้แล้ว และตารางบันทึกประวัติไม่มีวันถูกปิดใช้งาน |
| A15 | **ไม่เก็บ `ip` ในตารางธุรกิจ** เก็บเฉพาะใน log ที่มีอายุการเก็บกำกับ คือ log แบบ structured และตาราง `rest_log` (A42) ซึ่งเก็บ 90 วัน | IP address เป็นข้อมูลส่วนบุคคลตาม PDPA การเก็บลงทุกแถวโดยไม่มีวัตถุประสงค์เฉพาะเพิ่มภาระเมื่อเจ้าของข้อมูลใช้สิทธิขอลบ และขยายความเสียหายหากฐานข้อมูลรั่ว ส่วนการเก็บเฉพาะเหตุการณ์ยืนยันตัวตนมีวัตถุประสงค์ชอบธรรมชัดเจนคือการตรวจจับการเข้าถึงผิดปกติ |
| A16 | **ตาราง `tbl_audit_history` บันทึกทุกการแก้ไขและการปิดใช้งานของ 7 ตารางที่ตรวจสอบ** แบบ 1 การแก้ = 1 แถว ระบุ `table_name` `entity_id` `action` (`update` / `soft_delete` / `restore`) `old_json` `new_json` `changed_by` `changed_at` โดยเก็บเฉพาะคอลัมน์ที่เปลี่ยนจริง ยกเว้น `password_hash` payload ก้อนใหญ่ และคอลัมน์ snapshot · `activities` ไม่อยู่ในรายการเพราะเขียนอย่างเดียวอยู่แล้ว | CRM ต้องตอบลูกค้าได้ว่าตอนนั้นข้อมูลเป็นอย่างไรและใครแก้ การเก็บเป็น JSON ก้อนเดียวต่อการแก้หนึ่งครั้งทำให้แก้ 100 ฟิลด์พร้อมกันได้แถวเดียว ไม่ใช่ 100 แถว การปิดใช้งานถูกแยกเป็น action ต่างหากเพราะในสายตาผู้ใช้มันคือการลบ หน้าจอตรวจสอบจึงกรองได้ ที่ไม่เก็บ `password_hash` เพราะเป็นข้อมูลยืนยันตัวตนซึ่งไม่ควรมีอยู่สองที่ และที่ไม่เก็บ `raw_payload` หรือ `payload` เพราะตารางต้นทางเก็บไว้แบบไม่มีวันแก้อยู่แล้ว การคัดลอกซ้ำทุกครั้งที่สถานะเปลี่ยนจะทำให้คอลัมน์ที่ใหญ่ที่สุดในระบบทวีคูณโดยไม่ได้ประโยชน์ |
| A17 | **คอลัมน์ snapshot JSON ของเรคคอร์ดที่เกี่ยวข้อง**: `contacts.company_master_json` · `leads.contact_data_json` `company_data_json` `owner_data_json` · `activities.lead_data_json` `actor_data_json` · `messages.lead_data_json` `contact_data_json` · `ai_suggestions.lead_data_json` รวมถึง `activities.from_stage` / `to_stage` และ `ai_suggestions.context_snapshot` ทั้งหมด**ระบบเติมเองผ่าน hook เท่านั้น** โค้ดแอปพลิเคชันไม่เขียนโดยตรงสักที่ | ตอบคำถามว่าเรคคอร์ดนี้ผูกกับอะไรและอะไรมีหน้าตาอย่างไร ณ เวลาที่เขียน โดยค่าปัจจุบันยังอ่านจากการ join ผ่าน FK เสมอ เพราะเซลส์ต้องเห็นค่าล่าสุด ความเสี่ยงเรื่องข้อมูลสองที่หลุดจากกันถูกกำจัดด้วยการให้ hook เป็นทางเขียนทางเดียว สำเนาที่ต้องอาศัยคนจำว่าต้องอัปเดตคือสำเนาที่วันหนึ่งจะผิด แถวที่แก้ไขได้ (contacts, leads) จะรีเฟรช snapshot เมื่อ **FK เปลี่ยน** ไม่ใช่เมื่อบริษัทเปลี่ยนชื่อ เพราะการเปลี่ยนชื่อไม่ได้แปลว่าตอนนั้นบริษัทชื่ออื่น คำถามนั้นตอบด้วย `tbl_audit_history` (A16) ส่วนแถวที่เขียนอย่างเดียว (activities, messages, ai_suggestions) บันทึกครั้งเดียวตอนสร้าง snapshot เก็บเฉพาะตัวระบุและป้ายชื่อ ไม่เก็บเบอร์โทร อีเมลของลูกค้า และ LINE user id เพราะเป็นข้อมูลส่วนบุคคลที่ยังอ่านได้จากแถวจริง และการคัดลอกไปทุกที่จะขยายสิ่งที่ต้องตามลบตาม PDPA |

| A45 | **เบราว์เซอร์คุยกับ Next.js เท่านั้น ไม่ได้คุยกับ API โดยตรง** โดย Next.js ทำหน้าที่ proxy `/api` และ `/webhooks` ไปยัง Express ผ่าน rewrites · API ยังมีชั้น CORS แบบระบุรายชื่อกำกับไว้อีกชั้น ค่าเริ่มต้นคือไม่อนุญาตโดเมนใดเลย ตั้งเพิ่มได้ด้วย `CORS_ORIGINS` | Railway ให้แต่ละ service มีโดเมนของตัวเองใต้ `up.railway.app` ซึ่งอยู่ใน Public Suffix List ทำให้สองโดเมนนั้นถือเป็นคนละเว็บไซต์ในสายตาเบราว์เซอร์ cookie ที่ตั้ง `SameSite=Lax` จึงจะไม่ถูกส่งไป ทางแก้ที่ล่อใจคือลดเป็น `SameSite=None` ซึ่งเท่ากับลดความปลอดภัยของ cookie สำหรับผู้ใช้ทุกคน เพื่อแก้รายละเอียดของการติดตั้งเพียงเรื่องเดียว การ proxy ทำให้ cookie เป็น first-party และตัดเรื่อง CORS ออกไปทั้งหมด ส่วนชั้น CORS ที่เหลือไว้เป็นการป้องกันซ้อนสำหรับกรณีที่มีคนเรียก API ตรง โดยปฏิเสธเป็นค่าเริ่มต้น เพราะพฤติกรรมของไลบรารีที่ไม่ตั้งค่าคือสะท้อน `Origin` กลับไปทุกค่า ซึ่งเมื่อรวมกับ `credentials: true` จะทำให้เว็บไซต์ใดก็ได้ที่ผู้ใช้ซึ่งล็อกอินอยู่เปิดขึ้นมา เรียก API นี้ในนามของเขาได้พร้อม cookie |

## 8. สิ่งที่เลือกไม่ทำ

ทุกข้อคือการตัดออกอย่างตั้งใจ ไม่ใช่การมองข้าม เวลาที่ประเมินเป็นการประมาณของผมเอง

| สิ่งที่ตัด | เหตุผล | เวลาถ้าจะทำเพิ่ม |
|---|---|---|
| pipeline แบบลากวาง | เปลี่ยน stage ด้วยปุ่มให้ผลเท่ากันในเชิงหน้าที่ | ~3 ชม. |
| แดชบอร์ดรายงานและการพยากรณ์ | ไม่มี flow ที่ถูกประเมินข้อใดต้องใช้ | ~1 วัน |
| อีเมลและช่องทางอื่น | โจทย์กำหนดขอบเขตไว้ที่ LINE OA | ~2 วันต่อช่องทาง |
| นำเข้า/ส่งออกข้อมูลจำนวนมาก | ข้อมูลตั้งต้นครอบคลุมความต้องการของการสาธิตแล้ว | ~4 ชม. |
| custom field และ pipeline ที่ตั้งค่าได้ | เป็นฟีเจอร์ระดับผลิตภัณฑ์ ไม่ใช่ MVP | ~1 สัปดาห์ |
| อัปเดตแบบเรียลไทม์หลายผู้ใช้ | ผู้ใช้ 20 คนบน 300 lead แทบไม่ชนกัน การ poll ในหน้า lead เพียงพอ | ~2 วัน |
| หน้าดู audit log แยกต่างหาก | activity ถูกบันทึกและแสดงใน timeline ของ lead อยู่แล้ว แค่ไม่มีหน้าผู้ดูแลแยก | ~1 วัน |
| หน้าจอกู้คืนเรคคอร์ดที่ปิดใช้งาน | `is_active` ทำหน้าที่แทนการลบแล้ว (A14) แต่ยังไม่มีหน้าจอสำหรับดูและเปิดใช้งานกลับ ต้องแก้ผ่านฐานข้อมูล | ~4 ชม. |
| การรองรับหลายภาษา | เนื้อหาไทยและอังกฤษแสดงผลถูกต้อง แต่ส่วนติดต่อผู้ใช้เป็นอังกฤษอย่างเดียว | ~1 วัน |
| การตรวจสอบการเข้าถึงอย่างเป็นทางการ | ใช้ semantic HTML และควบคุมด้วยคีย์บอร์ดได้ แต่ยังไม่ได้ตรวจตามมาตรฐาน WCAG | ~1 วัน |

## 9. ความเสี่ยงที่รับไว้อย่างรู้ตัว

- **คุณภาพผลลัพธ์ของ LLM ยังไม่ถูกตรวจสอบกับผลการขายจริง** คะแนนอธิบายได้ แต่ยังไม่พิสูจน์ว่าทำนายได้ วิธีลดความเสี่ยงคือนำเสนอเป็นสัญญาณสำหรับจัดลำดับ ไม่ใช่เป็นคำตัดสิน
- **ติดตั้งภูมิภาคเดียวและไม่มี dead-letter queue** ข้อความที่ LINE ส่งมาระหว่าง deploy อาจตกหล่น การ retry ของ LINE ครอบคลุมกรณีส่วนใหญ่ และตาราง raw event ทำให้ replay ได้ แต่ยังไม่มีคิวรองรับจริง
- **ยังไม่ได้ทดสอบภาระงาน** ขนาดระบบมาจากการให้เหตุผลตามตัวเลขในโจทย์ ไม่ได้มาจากการวัด
- **รหัสผ่านบัญชีสาธิตเปิดเผยโดยตั้งใจ** ระบบที่ติดตั้งมีเฉพาะข้อมูลสังเคราะห์ และควรปิดหลังการประเมินเสร็จสิ้น
